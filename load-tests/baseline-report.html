Commentary Fan-Out Baseline

A single Node process held 500 concurrent WebSocket subscribers across five matches, took 20 commentary writes a second for four minutes, and delivered 271,901 frames with nothing lost and nothing failed — on eleven percent of one core. The interesting number is not the total. It is that only 1.5ms of the 102ms median belongs to the broadcast this project was about to rewrite.

Where the time actually goes

The database write is the latency. Fan-out is a rounding error.

A publish is measured end to end: the moment before the POST leaves, to the moment the WebSocket frame lands in a subscriber. Because the route replies before it broadcasts, that total splits cleanly into the HTTP request — validation plus the Neon INSERT — and everything the broadcast loop does afterwards.

Note the p99 at 100 connections is worse than at 500 — 412ms against 350ms. Fan-out cannot explain that, because fan-out went up. The tail is owned by database write variance, and the 100-connection plateau ran earlier, closer to Neon waking up.

How fan-out scales

Cost tracks subscribers per match, not subscribers total.

Commentary is delivered only to sockets subscribed to that match, so the broadcast loop is sized by the busiest match rather than by the server's connection count. Spreading the same 500 connections over five matches cut fan-out from 5.2ms to 1.5ms — the loop got five times shorter, and the cost fell with it.

What this changes about Phase 2

Redis pub/sub will not make this faster. It is a correctness fix.

Removing fan-out entirely would take the median from 102ms to about 100.5ms. The write is the latency, and Redis cannot make a Postgres INSERT quicker.

That does not make Phase 2 wrong — it changes what it is for. The moment there are two instances, a write landing on instance A must reach subscribers holding sockets on instance B, and matchSubscribers in ws/server.js is a per-process Map. Today that simply would not work. So the expected Phase 2 result is a median that barely moves and fan-out that now crosses instances. If the median improves noticeably, something else changed and it is worth finding out what.

  • The ceiling is nowhere near 500. Eleven percent of one core, flat memory, no loss. If a real limit exists it is well above this, and the p99 is where it will surface first.
  • Sharding by match already works. Fan-out is sized by the busiest match, so the cheapest scaling lever available today is spreading subscribers — which is also what makes a second instance viable.
  • Watch the write path instead. Doubling the write rate from 10/s to 20/s moved the median write from ~33ms to ~100ms. That is a threefold cost for a twofold load and it deserves its own measurement — pool contention and Neon behaviour are both plausible, and the two runs were a day apart, so this is a lead rather than a conclusion.

What this number is not

  • Loopback is not a network. Load generator and server share one machine, so there is no real network latency in any of these figures. Treat them as a floor.
  • Arcjet was switched off, and it is not free. A separate run with Arcjet back in the request path — at half this write rate, on one match — added a flat ~60ms per write and 8.5× the CPU. Whatever the write path costs in production, roughly 60ms of it is not yours.
  • Both third-party layers must stay off for Phase 2, or the comparison measures the wrong thing. The exact flags are recorded in each run's run-context.txt and visible in its server-stdout.txt.
  • Peak concurrency is cross-checked, not read directly. A read-only endpoint exposing wss.clients.size would measure it outright, and is worth adding before there is more than one instance to account for.

Reproducing it

cd load-tests
MATCH_COUNT=5 PLATEAUS=100,500 RAMP_S=30 HOLD_S=90 \
  PUBLISH_RATE=20 LABEL=mixed-load ./run-baseline.sh

The runner starts and stops the server itself, records the configuration it booted with, samples the process once a second, and refuses to run if something is already listening on the port — a server started by hand has unknown flags, and a measurement whose configuration you cannot state is not comparable to anything.

Test data is labelled and disposable: every run creates fresh matches with sport = 'loadtest', and commentary.match_id cascades on delete.
