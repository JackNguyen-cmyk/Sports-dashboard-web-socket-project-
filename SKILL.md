# 1. What this project is

**To a non-technical friend:** a live sports ticker. Open a match and every
goal, card and substitution appears on your screen the moment it is recorded,
without refreshing.

**To an engineer:** an Express 5 HTTP API and a `ws` WebSocket server sharing
one `http.Server`, backed by Neon Postgres through Drizzle. Writes go
`Zod → INSERT → respond 201 → broadcast`. A new match is announced to every
socket; commentary is fanned out only to sockets that subscribed to that match
(`Map<matchId, Set<socket>>`). Rate limiting on both HTTP and the WebSocket
upgrade, a ping/pong heartbeat that reaps half-open sockets, and a k6 harness
that measured the whole path at 500 concurrent subscribers.

# 2. Problem it solves

Polling `GET /commentary` every few seconds from thousands of clients is the
obvious design and it is wrong twice over: it hammers the database with reads
that mostly return nothing new, and a viewer still sees a goal up to one poll
interval late. Push over WebSocket makes the cost of delivery scale with
*viewers of that match × events in that match*, not *viewers × poll rate*, and
the measured delivery latency is ~100 ms end to end — almost all of which is the
database write, not the push.

The honest version: the immediate reason it exists is to learn backend
engineering properly — stateful connections, failure modes around `await`,
measuring before optimising. It was built so that every claim in the README has
a load-test run or a regression test behind it. The live-data source
(OpenLigaDB, stage 7 of `ROADMAP.md`) is chosen but not yet wired in, so today
every event is typed in by hand or generated by the load test.

# 3. Architecture

```
                 ┌──────────────────────────────────────────────┐
  HTTP  ───────▶ │  Express 5                                    │
                 │   express.json → Arcjet rate limit → routers  │
                 │                                               │
                 │   POST /matches ──────────┐                   │
                 │   POST /matches/:id/commentary ─┐             │
                 │                           │     │             │
                 │             Zod validate ─┴─────┴─▶ Drizzle ──┼──▶ Neon Postgres
                 │                                   │           │
                 │                              broadcast        │
                 │                                   │           │
  WS  ─────────▶ │  ws  (/ws, same HTTP server)      ▼           │
   subscribe ──▶ │   matchSubscribers: Map<matchId, Set<socket>> │
   ◀── events    │   heartbeat reaps dead sockets every 30s      │
                 └──────────────────────────────────────────────┘
```

Components — responsibility — why this and not the alternative:

- **`src/index.js`** — loads dotenv, starts the APM agent, calls `createApp({ db })`
  and `server.listen()`. The *only* place the real database is wired in. Import
  order is load-bearing (dotenv → agent → app) and commented as such.
- **`src/app.js` — `createApp({ db })`** — builds Express + `http.Server` without
  listening. A factory, not a module-level `app`, because a module evaluates once
  per process and every test would share one app with no way to inject a fake.
- **Express 5** — HTTP API. Chosen over Express 4 because it forwards errors from
  `async` handlers without a wrapper (verified). Chosen over Fastify/Nest because
  the point was to learn the mechanics, not a framework's opinion of them.
- **`ws`** — the WebSocket layer, on the *same* `http.Server` so an upgrade hits
  the same rate limiter as an HTTP request. `ws` over Socket.IO deliberately:
  bare protocol, standard close codes (1008/1011/1013), no invisible reconnect
  or room magic — every behaviour is something I wrote and can explain.
- **`src/ws/server.js` — `attachWebSocketServer(server, { arcjet, heartbeatIntervalMs })`**
  — subscriptions, broadcast, heartbeat, and the pre-auth message queue. Both
  dependencies are injectable; that is what made the Stage 0 bugs testable.
- **Neon Postgres via Drizzle** — serverless Postgres so there is nothing to host
  yet; Drizzle because the schema is plain JS and the SQL it generates is
  readable. The database enforces the invariants (native `match_status` enum,
  unique `(match_id, sequence)`, cascade on delete) so the app maps SQLSTATE to
  4xx instead of pre-checking.
- **Zod 4** — validation at the HTTP boundary. `z.coerce` only for path and query
  params, where values genuinely arrive as strings; plain `z.number()` for JSON
  bodies (see section 7 for why).
- **Arcjet** — sliding-window rate limit + shield + bot detection on both HTTP
  (50 / 10 s) and WS upgrades (5 / 2 s). Chosen over a hand-rolled Redis limiter
  because there is no Redis yet; its cost is measured (+~60 ms/request) rather
  than assumed.
- **`node:test`** — no test framework dependency. 23 tests: 18 for the match
  status state machine, 5 WebSocket regression tests.
- **k6 (`load-tests/`)** — a separate Go binary, kept outside `src/` because it is
  not part of the deployed app. Three recorded runs with raw output committed.

# 4. Key decisions and trade-offs

| Decision | Options I considered | What I chose | Why | What I gave up |
|---|---|---|---|---|
| One HTTP server for both protocols | Separate ports / processes for HTTP and WS | Shared `http.Server`, `server.listen()` | One rate limiter covers both; one port to deploy. Also the source of a real bug — `app.listen()` silently creates a *second* server | Scaling HTTP and WS independently |
| When to broadcast | Inside the insert's `try`; after it; after `res.json()` | Respond 201 first, then broadcast in its own `try` | The row is committed; a notification failure must not turn a success into a 500 that invites a retry into a 409 | The client cannot know whether the broadcast happened |
| Fan-out scope | Broadcast everything to everyone | `matchCreated` → all; `commentaryCreated` → subscribers of that match only | Cost scales with viewers-of-that-match, not viewers × events. Measured: 500 sockets on 1 match = 5.2 ms fan-out, spread over 5 matches = 1.5 ms | A per-socket subscription set that must be bounded and cleaned up — both of which went wrong once |
| Fail open vs fail closed when Arcjet errors | Same policy for both; fail open; fail closed | HTTP fails **open**, WS fails **closed** | An HTTP request that slips through is over in ms; an unvetted socket persists for hours. The asymmetry is a decision, commented at both call sites | Consistency; a reviewer has to read two comments |
| Coercion in schemas | `z.coerce.number()` everywhere; nowhere; per-source | Coerce path/query only; plain `z.number()` for bodies | `Number(null)` is `0`, so a coerced body stored `"minute": null` as minute 0 with no error | Clients that send `"5"` in a JSON body now get a 400 |
| Constraint errors | Pre-check with a `SELECT`; let it 500; map SQLSTATE | Map `23503` → 404, `23505` → 409 from `error.cause.code` | A pre-check is a race (TOCTOU); the database already knows. A 500 tells the client to retry something that can never succeed | A dependency on Drizzle's error shape (`cause`, not `code`) |
| Who assigns `sequence` | Server auto-increment; client-supplied | Client-supplied, unique per match | Makes writes idempotent by slot — a re-sent event is a 409, not a duplicate. This is what makes stage 7 (re-polling an upstream API) safe | The client has to coordinate sequence numbers |
| The Arcjet check inside an `async` connection handler | Register handlers after the await; before it; queue messages | `'error'`, `'close'`, `'message'` all registered **before** the await; messages queued (max 20) and drained after | Node drops `'message'` with no listener, and throws on `'error'` with no listener. During the 47–226 ms check the socket had neither | 20 lines of ordering that must be read to be believed — hence the comment block and 5 regression tests |
| How to make that testable | Test with a real Arcjet key; mock the module; inject | `attachWebSocketServer(server, { arcjet })` and `createApp({ db })` | Without a key there is no `await`, so the window — and the bugs — do not exist. A parameter can be a `setTimeout` stand-in | A little ceremony in `index.js` |
| Disable flag semantics | Truthiness; exact string | `ARCJET_ENABLED === 'false'` only | A typo (`flase`, `0`) leaves protection **on**. Verified by booting with the typo. The APM agent gets this backwards and I documented that in `.env.example` | Nothing meaningful |
| Half-open socket handling | Trust `readyState`; `close()`; `terminate()` | 30 s ping/pong sweep, `terminate()` on miss | A NAT timeout leaves `readyState === OPEN` forever; a half-open socket never completes a close handshake | A 30–60 s window where a dead socket still counts |
| Redis pub/sub now or later | Now (it was Phase 2 of the first roadmap) | Later — after tests, domain model, shutdown, deploy | The baseline showed fan-out is 1.5 ms of a 102 ms median. Redis is a *correctness* fix for multi-instance, not a speed-up; and the app could not yet update a score | The "scaled it horizontally" bullet, for now |

# 7. Things that broke and how I fixed them

Every entry here is a bug that actually occurred, with the commit behind it.
These are the ones an interviewer should ask about.

1. **Symptom:** Nothing. Reading `ws/server.js`, `socket.on('message')` was
   registered *before* an awaited Arcjet call with a comment explaining why —
   but `'error'` and `'close'` were registered *after* it.
   **Cause:** `ws` emits `'error'` on the socket for any protocol violation
   (frame over `maxPayload`, bad UTF-8), and Node throws on an `'error'` event
   with no listener. So for the 47–226 ms of the check, any unauthenticated
   client could crash the process with one oversized frame. Same window:
   `'close'` fires once, so a socket that left mid-check had its close land on
   nothing, then the queue drained and added a CLOSED socket to
   `matchSubscribers` forever. It was production-only — without an Arcjet key
   there is no `await`, so the window does not exist locally.
   **Fix:** Hoist both handlers above the await. Hoisting `'close'` was
   necessary but not sufficient — the drain also needs
   `if (socket.readyState !== WebSocket.OPEN) return;` because the close has
   already fired. Made `arcjet` injectable so a `setTimeout` could stand in for
   it; wrote 5 regression tests that fail 5/5 against the old ordering.
   Reproduced the crash first: `UNCAUGHT EXCEPTION -> Max payload size exceeded`.
   **Lesson:** When one listener is hoisted for a reason, that reason applies to
   its siblings. Every long-lived emitter gets an `'error'` listener even if it
   does nothing — which is why `pool.on('error')` went into `db/db.js` the same
   day. And: a bug that only exists inside an `await` is invisible to a test
   suite that never awaits.

2. **Symptom:** A client that sent `subscribe` immediately on open never got
   `subscribed`; the same message a moment later worked. Looked like a flaky
   test.
   **Cause:** The connection handler awaited Arcjet before registering
   `socket.on('message')`. Node drops a `'message'` with no listener. Timed the
   await at 47–226 ms; reproduced in isolation with a `setTimeout` — of two
   messages only the later one arrived.
   **Fix:** Register the listener immediately, queue up to 20 messages, drain
   after the decision.
   **Lesson:** An `async` event handler leaves a window in which the listeners it
   registers do not exist yet.

3. **Symptom:** Requests were rejected "a bit early" — easy to dismiss as the
   limiter being approximate.
   **Cause:** Measured instead of reading: 60 rapid requests, `/` allowed 49 and
   `/matches` allowed 25. One limiter cannot apply two limits, so it was
   structural: Arcjet was registered twice (an inline middleware plus the
   refactored `securityMiddleware()`), and `/matches` sat below both, consuming
   the quota twice per request. `/` sat above one of them.
   **Fix:** Delete the inline copy; register the survivor above every route.
   **Lesson:** "Roughly half" is a number with a cause. Middleware order is
   registration order, and doubling a protection doubles its cost and its bill.

4. **Symptom:** Every match was `finished` before kickoff — but only some, so it
   looked intermittent.
   **Cause:** `new Date(null)` is the Unix epoch, not an invalid date, so the
   `Number.isNaN(end.getTime())` guard passed and `now >= end` was true for
   every match with a NULL `end_time`. Found by testing `endTime: undefined`
   (returned `null`) and `endTime: null` (returned `finished`) separately.
   **Fix:** Handle the absent value before ever parsing it.
   **Lesson:** Wrote 18 tests and ran them against the *old* code first — 5
   failed. A suite that cannot fail against the bug it describes proves nothing.

5. **Symptom:** `POST /matches/:id/commentary` returned 500 for both a
   duplicate `sequence` and a nonexistent match, despite explicit handling for
   `23505` and `23503`.
   **Cause:** Drizzle wraps driver errors in a `DrizzleQueryError` whose own
   `code` is `undefined`; the SQLSTATE is on `error.cause.code`. Printed the
   actual error shape instead of trusting the assumption.
   **Fix:** `error?.cause?.code ?? error?.code`. Duplicate → 409, missing → 404.
   **Lesson:** When branching on an error, print its real shape first. And a 500
   for a constraint violation is worse than no handling — it tells the client to
   retry something that can never succeed.

6. **Symptom:** `"minute": null` in the body was stored as `0`. No error
   anywhere; the API said 201.
   **Cause:** `z.coerce.number()` is `Number()` underneath. `Number(null)` is
   `0`, `Number(true)` is `1`, `Number([])` is `0`. Coercion had been copied
   from the query-param schemas, where it is correct.
   **Fix:** Plain `z.number()` for body fields; also bounded every integer to
   `2_147_483_647` because oversized values were passing validation and failing
   at insert with `22003` — another 500 for a bad request.
   **Lesson:** The same bug sat in the *match* schema for two more days after
   the commentary fix. When a bug is a class, grep for the pattern before
   closing it.

7. **Symptom:** A k6 run configured for 4 m 40 s took 8 m 04 s and reported
   253,225 iterations for ~3,300 real requests.
   **Cause:** `iteration_duration` median 16.25 µs — not a network round trip, a
   function returning immediately. An early `return` in the end-of-run guard,
   under `ramping-vus`, is a hot loop. The first fix, `sleep(Math.max(remainingMs, 0))`,
   spun the same way because `remainingMs` goes negative past the nominal end and
   `sleep(0)` returns immediately.
   **Fix:** `sleep(Math.max(remainingMs / 1000, 1))`. 14,963 → 40 iterations.
   **Lesson:** Before deciding whether to re-run, establish whether the
   measurement was affected: the guard fires after 275 s and the last plateau
   ends at 270 s, so no plateau number was touched. Load-test harnesses have
   bugs too; check the tool's own metrics before believing its results.

8. **Symptom:** HTTP routes all returned 200; WebSocket clients could not
   connect. No error, no log.
   **Cause:** `http.createServer(app)` with `ws` attached, then `app.listen()` —
   which creates a *second* HTTP server. The one holding the upgrade handler was
   never listening.
   **Fix:** `server.listen()`.
   **Lesson:** When one protocol works perfectly and the other silently does
   not, look at what they are supposed to share.

# 8. What I would do differently at 100× scale

Today's measured point is 500 subscribers and 20 writes/s. Call 100× 50,000
subscribers and 2,000 writes/s.

- **The write path breaks first, and Redis will not save it.** Each `INSERT`
  costs ~100 ms at 20/s against Neon (and it was ~33 ms at 10/s — that 3×
  jump is stage 9's open lead). At 2,000/s with `pg`'s default pool of 10, ~200
  writes would be in flight at any moment against 10 connections: queueing
  starts immediately. I would move the durable write off the request path —
  accept the event, append it to a log (Postgres `LISTEN/NOTIFY` is too weak; a
  real queue), and let a consumer batch inserts. The client-supplied
  `sequence` with its unique index is what makes replaying that queue safe.
- **Fan-out needs more than one process, and that is a correctness change, not a
  latency one.** `matchSubscribers` is a per-process `Map`; with two instances
  a write on A never reaches a subscriber on B. Redis pub/sub keyed by
  `matchId` fixes that. At 5.2 ms per 500 sockets on one match, 50,000 on one
  match would be ~0.5 s of synchronous `send()` per event on one core, so the
  sockets have to be spread across instances *and* the per-instance loop has to
  yield. I would expect the median not to move after this, and would treat it
  as a bug if it did.
- **One slow client currently slows the broadcast for everyone, and a
  reconnecting client loses everything it missed.** `client.send()` is called
  in a loop with no check on `socket.bufferedAmount`; at 50,000 sockets a few
  stalled TCP windows would hold the event loop. I would pick a policy (drop
  frames above a buffer threshold, or disconnect with 1013) and add
  `since=<sequence>` replay on reconnect — which the unique
  `(match_id, sequence)` index already makes well-defined.

**Q1. You run this on two servers. A goal is POSTed to server A, and the viewer
is connected to server B. What happens today — and what does Redis pub/sub
change about your latency numbers?**

Facts the answer must contain:
- Today: nothing reaches B. `matchSubscribers` is an in-memory `Map` in one
  process; A broadcasts to its own sockets only.
- Redis pub/sub: A publishes to a channel per match; every instance subscribes
  and fans out to *its* sockets. The map stays per-process; only the event
  crosses instances.
- Latency: the median will not move, and I have the number that says why — of
  the 102 ms median, 100.5 ms is the Neon INSERT and 1.5 ms is fan-out. Redis
  cannot make an INSERT faster. If p50 improves after Phase 2, something else
  changed and I would go find it.
- What it costs: a Redis dependency, one more network hop (~sub-ms locally),
  and at-most-once delivery across the bus — a subscriber on B that misses a
  message has no replay unless I add `since=<sequence>` (stage 12).

**Q2. Your p50 is 102 ms and your p99 is 350 ms. Where does the tail come from,
and how do you know it isn't your broadcast loop?**

Facts the answer must contain:
- Decomposition: the route responds before it broadcasts, so the k6 publisher
  records the HTTP request on its own (`post_duration`); e2e minus that is the
  fan-out share. Fan-out is 1.5 ms at p50 and cannot produce a 250 ms tail.
- Cross-check from the data: the p99 at 100 connections (412 ms) was *worse*
  than at 500 (350 ms), while fan-out rose. The tail belongs to write variance,
  not fan-out. The 100 plateau ran first, closer to Neon waking up.
- Percentiles tagged per plateau, not across the whole ramp — otherwise a run
  that ramps 50 → 200 → 500 blends three regimes and the p99 describes nothing.
- The suspect: Neon write variance and pool contention (`pg` default 10
  clients). Writes went 33 → 100 ms when publish rate doubled. That is a lead
  I have written down (stage 9), not a conclusion — the runs were a day apart,
  so I would change one variable at a time: pool size first, then rate.

**Q3. A client opens a WebSocket and sends `subscribe` in the same tick. Walk me
through exactly what happens between the upgrade and the `subscribed` ack — and
what used to go wrong.**

Facts the answer must contain:
- `wss.on('connection')` is `async` and awaits an Arcjet decision — a network
  call, measured 47–226 ms.
- Before that await, three listeners are registered: `'error'` (else a bad
  frame is an uncaught exception — one frame could kill the process,
  unauthenticated), `'close'` (fires once; miss it and the socket's
  subscriptions are never cleaned), and `'message'` (Node drops a message with
  no listener — the `subscribe` vanished).
- Messages that arrive during the check go into a bounded queue (20). After the
  decision: denied → close with 1013 (rate limit, retry later) or 1008 (policy,
  don't); errored → 1011, fail *closed* unlike the HTTP path; allowed → check
  `readyState` is still OPEN (the client may have left mid-check; its close
  already fired), send `welcome`, drain the queue in order.
- The three original bugs and why they were invisible: with no Arcjet key there
  is no await, so the window does not exist locally. Made `arcjet` a parameter
  so a `setTimeout` could stand in; 5 tests fail 5/5 against the old ordering.

**Q4 (the one that always comes). Why does the HTTP path fail open and the
WebSocket path fail closed when the rate limiter is down?**

Facts: an HTTP request that slips through is over in milliseconds; an unvetted
socket persists for hours and holds server state. Both are commented at the call
site. The alternative — a 503 on HTTP — is one line and is the right call if
rejecting unvetted traffic matters more than staying up.

# 10. Honest limitations

- **Not deployed.** No public URL, no CI, no Dockerfile. Every claim is
  reproducible locally and nowhere else.
- **No authentication on writes.** Anyone who can reach the API can `POST`
  commentary to any match. Rate limiting is the only gate (stage 5).
- **The domain model is incomplete.** A score cannot be updated
  (`updateScoreSchema` has no endpoint) and a match created as `scheduled`
  stays `scheduled` forever — `syncMatchStatus` exists and is called by nothing
  but its own tests (stage 3). This is the gap the load-test numbers distracted
  me from — interesting measurements pull attention toward optimising the path
  that exists and away from noticing the path that does not.
- **Single instance only.** `matchSubscribers` is per-process; a second
  instance would silently split the audience.
- **No graceful shutdown.** A restart drops every live connection and abandons
  the pg pool mid-flight (stage 4).
- **No backpressure.** One slow client slows the broadcast loop for everyone.
  No replay on reconnect — a viewer that drops for 5 s misses those events.
- **Only two of four layers are tested.** The status helper and the WS server
  have tests; every HTTP route has only ever been checked by hand with `curl`.
- **The load test ran over loopback** with generator and server on one machine.
  The numbers are a floor. The 3× write-latency jump is unexplained.
- **No real data yet.** OpenLigaDB is chosen (German football only; goals but
  not cards or substitutions; crowd-sourced freshness) but no code calls it.
- **Arcjet's sliding window is evaluated before it increments**, so ten
  simultaneous upgrades all pass while sequential ones are refused from the
  6th. It throttles sustained load, not an instantaneous burst. Known, not
  fixed, and it makes back-to-back tests flaky.

# 11. How to run it

Everything lives under `src/` — `package.json`, `node_modules`, `.env`. Run every
command from there; `npm install` from the repository root creates a stray
manifest that nothing uses.

```bash
git clone https://github.com/JackNguyen-cmyk/Sports-dashboard-web-socket-project-.git
cd Sports-dashboard-web-socket-project-/src
npm install
cp .env.example .env        # fill in DATABASE_URL at minimum
npm run db:migrate           # applies drizzle/ migrations
npm run dev                  # http://localhost:8000, ws://localhost:8000/ws
npm test                     # 23 tests, no database needed
```

Required environment variables:
- `DATABASE_URL` — a Postgres connection string (Neon, or any Postgres)
- `PORT`, `HOST` — default `8000`, `0.0.0.0`
- `ARCJET_KEY` — optional; leave empty and protection is off with a warning
- `ARCJET_ENABLED=false` — takes Arcjet out of the path entirely (load tests)
- `ARCJET_ENV`, `ARCJET_MODE` — `development` / `LIVE`; `DRY_RUN` evaluates but
  never blocks and still costs the network call
- `APMINSIGHT_*` — optional APM agent; set `APMINSIGHT_AGENT_DISABLE=true` or
  leave it unset, never `false` (see `.env.example` for why)

Load tests need [k6](https://k6.io) and write real rows:

```bash
cd load-tests && ./run-baseline.sh
```
